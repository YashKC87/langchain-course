This document explains **every major element** of the lab in technical detail, framed for a live or recorded use-case demonstration. Use it with the UI dropdown pages (**Overview**, **AI Model Operations**, **Model Comparison**) and the pattern detail views opened from Overview.

## 1. Business use case

### Problem

Digital workplace / endpoint fleets generate mixed workloads:

| Workload type | Examples | Wrong default |
|---|---|---|
| Routine, high volume | Health status, crash counts, known SOP steps | Sending all of this to Frontier wastes capacity and money |
| Hard reasoning | Multi-domain RCA, ambiguous Teams+VPN, synthesis | Sending all of this to SLM risks low-quality answers |

### Solution demonstrated

**Right Model Lab** shows a hybrid architecture:

- **SLM** = experienced Service Desk Engineer — fast, lower cost, strong on known work  
- **Frontier** = Senior Solution Architect — planning, ambiguity, cross-domain synthesis  

Principle locked into the product:

> Use the right model for the right task.

The lab does **not** claim “replace Frontier with SLMs.” It proves disciplined collaboration with measurable evidence.

### Primary success metric

**Frontier tokens avoided** — hybrid execution versus an **ESTIMATED ALL-FRONTIER BASELINE**.

Fewer total tokens is **not** automatically better if quality collapses.

---

## 2. What you will demonstrate (end-to-end)

1. A synthetic endpoint fleet and locked incidents power five architecture patterns.  
2. Each pattern routes work through explicitly labeled **SLM / FRONTIER / NON-LLM** steps.  
3. Every step records tokens, latency, confidence, cost, and provenance.  
4. Overview tells the story per pattern; AI Model Operations shows portfolio evidence; Model Comparison audits selected vs alternative.  
5. Demo Mode works offline; Live Mode can use Ollama (SLM) and Azure OpenAI (Frontier), with optional LangSmith.

---

## 3. System architecture (technical)

```
UI (Streamlit — Right Model Lab)
        │
        ▼
ScenarioService  ──────────► ResultStore (.local_pattern_results.json)
        │
        ├── Pattern engines (5)
        │     ├── LanguageModel factory → Demo / Ollama / Azure
        │     ├── TelemetryService + VectorStore (RAG)
        │     └── BaselineEstimator (ESTIMATED all-Frontier)
        │
        └── LangSmithTracer ──► TraceStore (.local_traces.json)
                                 └── optional LangSmith remote
```

| Layer | Module(s) | Responsibility |
|---|---|---|
| UI | `app/ui/dashboard.py`, charts, architecture components | Demonstration surface |
| Orchestration | `app/services/scenario_service.py` | Run one/all patterns, KPIs |
| Patterns | `app/patterns/*.py` | Locked scenario logic |
| Models | `app/models/*` | Provider-agnostic inference |
| Data | `app/data/*` | Synthetic fleet + SOP KB |
| Observability | `app/observability/*` | Metrics, traces, cost |
| API | `app/main.py` | Same orchestration over HTTP |

## 4. Synthetic data elements

### 4.1 Device fleet

Generated by `app/data/generator.py` (`n=100`, `seed=42`) into `app/data/devices.csv`.

Fields include CPU/memory/disk, Teams crashes, VPN disconnects, OneDrive sync errors, Wi‑Fi, latency, packet loss, compliance, DEX score, risk score, region, OS, device type.

**Risk buckets** (Overview fleet strip):

| Bucket | Rule |
|---|---|
| Healthy | `risk_score < 30` |
| At risk | `30 ≤ risk_score < 70` |
| Critical | `risk_score ≥ 70` |

### 4.2 Locked demonstration devices

| Device | Pattern(s) | Why it exists |
|---|---|---|
| `LAPTOP-1204` | Planner-Worker, Fallback | Multi-domain stress: high CPU/mem, Teams crashes, VPN issues, poor DEX — needs plan + workers + synthesis |
| `LAPTOP-9910` | Confidence Cascade | Ambiguous Teams + VPN + Wi‑Fi conflict — first-pass SLM confidence is intentionally low |
| `LAPTOP-1507` | RAG | Disk nearly full + OneDrive sync errors — perfect for SOP retrieval |
| `LAPTOP-3304` | Cascade smoke (tests) | Healthy device for high-confidence non-escalation path |

### 4.3 Incidents

`app/data/incidents.csv` — categories such as CPU Saturation, Memory Pressure, Teams Crash, VPN Disconnect, Disk Full, OneDrive Sync, Compliance Drift, Wi‑Fi Instability. Extra history is attached to the locked devices so RCA prompts have context.

### 4.4 Knowledge base (RAG)

Markdown SOPs under `app/data/knowledge_base/` (disk, OneDrive, Teams, VPN, CPU, Intune compliance, BitLocker, patch management).

Indexed at runtime by `VectorStore` (TF‑IDF + cosine similarity, top‑k retrieval). No external vector DB required for the lab.

## 5. Model layer elements

### 5.1 Interface

`LanguageModel` (`app/models/model_interface.py`) exposes:

- `generate`, `structured_generate`, `classify`, `summarize`, `health_check`, `get_usage`

Patterns never import Azure or Ollama SDKs directly.

### 5.2 Model types and roles

| `ModelType` | Meaning in UI |
|---|---|
| `SLM` | Small / local model path |
| `FRONTIER` | Premium reasoning path |
| `NON_LLM` | Rules, routers, retrievers, evaluators |

Roles include: `planner`, `worker`, `router`, `synthesizer`, `diagnoser`, `generator`, `classifier`, `fallback`, `evaluator`, `retriever`.

### 5.3 Factory selection

`app/models/factory.py`:

| Condition | SLM client | Frontier client |
|---|---|---|
| `DEMO_MODE=true` or incomplete Azure config | `DemoSLMClient` | `DemoFrontierClient` |
| Live + Ollama | `LocalSLMClient` | — |
| Live + Azure configured | — | `AzureFrontierClient` |

### 5.4 Provenance (critical demo element)

| Label | Meaning | When you see it |
|---|---|---|
| **ACTUAL** | Provider-reported token usage | Live Ollama/Azure returned usage |
| **SIMULATED** | Deterministic demo telemetry | Demo Mode / many NON_LLM steps |
| **ESTIMATED** | Projection only — not a real call | All-Frontier baseline, alternatives |

**Demo talking point:** Never present ESTIMATED as money already spent or tokens already consumed.

## 6. Baseline estimator element

**Class:** `BaselineEstimator` (`app/services/baseline_estimator.py`)

- Holds task benchmarks (tokens, latency, confidence) for planning, workers, RCA, RAG, cascade, etc.
- Builds an **ESTIMATED ALL-FRONTIER BASELINE** for the same task list the hybrid ran.
- Explicitly does **not** call Frontier solely to invent that comparison.

**Demo talking point:** “We compare hybrid spend against a modeled all-Frontier path so we can talk about avoidance without burning Frontier capacity for the slide.”

## 7. Observability elements

### 7.1 TokenMetrics

Each span/segment records pattern, scenario, device, segment name, model name/type/role, provider, input/output/total tokens, latency, illustrative cost, confidence, provenance, and metadata (escalation, fallback, retrieval, etc.).

### 7.2 TraceStore

Local JSON store (`.local_traces.json`):

- Parent/child runs
- Filters by pattern, model type, device, escalated, fallback
- Aggregates for MLOps KPIs

### 7.3 LangSmithTracer

- Always writes local spans
- Optionally mirrors to LangSmith when `LANGSMITH_ENABLED`, `LANGSMITH_TRACING`, and `LANGSMITH_API_KEY` are set
- Sanitizes secrets from metadata

### 7.4 Cost calculator

Illustrative USD per 1K tokens from `.env` (defaults: SLM cheap, Frontier expensive). Labeled as illustrative — not market pricing.

## 8. Orchestration elements

### ScenarioService

- `run_pattern(pattern_id, **kwargs)` — execute one locked scenario  
- `run_all()` — execute all five  
- `overview_cards()` / `mlops_dashboard()` — UI payloads  
- Router accepts `n` (default 100); Fallback accepts `failure_type`

### ResultStore

Persists latest `PatternResult` per pattern to `.local_pattern_results.json`.

**Demo tip:** Use **Load latest saved result** for smooth room demos; live provider calls can take minutes.

## 9. The five patterns — technical demonstration detail

Each pattern appears as a tile on **Overview**. Open a tile to see:

1. Architecture diagram (SLM / FRONTIER / NON-LLM lanes)  
2. Execute / Load controls  
3. Explainable sections after a run  

---

### 9.1 Planner-Worker Hierarchy

| Item | Detail |
|---|---|
| Pattern ID | `planner_worker` |
| Device | `LAPTOP-1204` |
| Scenario | Complete multi-domain RCA |
| Primary benefit | Selective reasoning + orchestration efficiency |

**Technical flow**

| Step | Segment | Type | Role | What it does |
|---|---|---|---|---|
| 1 | Planning | FRONTIER | Planner | Breaks RCA into worker tasks |
| 2 | CPU Analysis | SLM | Worker | Routine OS/CPU/memory interpretation |
| 3 | Teams Analysis | SLM | Worker | Client crash signals |
| 4 | Network/VPN Analysis | SLM | Worker | Connectivity signals |
| 5 | Compliance Analysis | SLM | Worker | Compliance posture |
| 6 | History Analysis | SLM | Worker | Prior incidents |
| 7 | RCA Synthesis | FRONTIER | Synthesizer | Merges evidence into final RCA |

**What to say in the demo**

> Frontier is used twice — plan and synthesis. The five workers are SLM because those checks are repetitive telemetry interpretation. That is selective reasoning: premium capacity only where orchestration and judgment matter.

**Evidence to point at**

- Architecture diagram: Plan → Execute → Synthesize  
- “Why not Frontier for CPU?” style comparison on a worker segment  
- Token chart: hybrid Frontier tokens much lower than estimated all-Frontier  
- AI Architect Decision: Frontier tokens avoided  

---

### 9.2 Router Pattern

| Item | Detail |
|---|---|
| Pattern ID | `router` |
| Volume | 100 seeded endpoint health requests |
| Primary benefit | High-volume inference efficiency |

**Technical flow**

| Step | Segment | Type | Role | What it does |
|---|---|---|---|---|
| 1 | Router | NON_LLM | Router | Rules classify routine vs complex |
| 2…101 | `REQ-001`…`REQ-100` | SLM or FRONTIER | Classifier / Synthesizer | Routine → SLM; complex → Frontier |

**Mix (forced for clear demos):** ~**85 routine → SLM**, ~**15 complex → Frontier**.

Routine examples: CPU/disk/compliance status, crash counts, simple health classification.  
Complex examples: cross-domain RCA, novel/ambiguous telemetry, complex UX degradation.

**What to say**

> The router itself is not an LLM. It is a dispatcher. Most volume never deserves Frontier. A minority of hard requests still get the architect.

**Evidence**

- Router NON_LLM node  
- SLM vs Frontier request counts  
- High Frontier avoidance rate on AI Model Operations charts  

---

### 9.3 Confidence Cascade

| Item | Detail |
|---|---|
| Pattern ID | `confidence_cascade` |
| Device | `LAPTOP-9910` |
| Threshold | `CONFIDENCE_THRESHOLD` default **0.85** |
| Primary benefit | Quality-aware escalation |

**Technical flow**

| Step | Segment | Type | Role | What it does |
|---|---|---|---|---|
| 1 | SLM Initial Diagnosis | SLM | Diagnoser | First-pass RCA |
| 2 | Confidence Evaluator | NON_LLM | Evaluator | Reads confidence |
| 3 | Escalation Decision | NON_LLM | Evaluator | Accept or escalate |
| 4 | FRONTIER RCA | FRONTIER | Synthesizer | Only if below threshold |

**Locked demo path:** SLM confidence forced around **0.54** → escalate (because the scenario is intentionally ambiguous).

**Honest economics (important)**

An escalated single incident can cost **more** than calling Frontier directly (SLM attempt + Frontier). The lab still shows **fleet** economics: most incidents stop at SLM; only uncertain ones escalate.

**What to say**

> This is not “always cheapest model.” It is “try the service desk first; escalate when confidence is insufficient.” Quality gate first, savings at fleet scale.

**Evidence**

- Confidence 0.54 vs threshold 0.85  
- Escalation segments  
- Options table: SLM only / Frontier only (ESTIMATED) / Cascade  
- Fleet economics callout  

---

### 9.4 Retrieval-Augmented Generation (RAG)

| Item | Detail |
|---|---|
| Pattern ID | `rag` |
| Device | `LAPTOP-1507` |
| Primary benefit | Grounded enterprise knowledge with a smaller model |

**Technical flow**

| Step | Segment | Type | Role | What it does |
|---|---|---|---|---|
| 1 | Query Analysis | NON_LLM | Evaluator | Normalize the ticket/question |
| 2 | Retrieval | NON_LLM | Retriever | TF‑IDF search over SOP KB |
| 3 | Document Ranking | NON_LLM | Retriever | Rank chunks |
| 4 | Context Construction | NON_LLM | Retriever | Build grounded context |
| 5 | SLM Grounded Generation | SLM | Generator | Produce remediation with citations |

**What to say**

> Retrieval supplied the domain knowledge. That is why Frontier is not required here. The SLM answers from approved SOPs instead of inventing procedure.

**Evidence**

- Retrieved chunk list / citations  
- Grounding score  
- RAG+SLM vs ESTIMATED RAG+Frontier comparison  
- No Frontier segment in the selected path  

---

### 9.5 Designing for Fallback

| Item | Detail |
|---|---|
| Pattern ID | `fallback` |
| Device | `LAPTOP-1204` |
| Primary benefit | Resilience and availability |
| Failure modes | `http_503`, `timeout`, `rate_limit`, `auth_error`, `offline`, `cost_guard` |

**Technical flow**

| Step | Segment | Type | Role | What it does |
|---|---|---|---|---|
| 1 | FRONTIER Attempt | FRONTIER | Synthesizer | Primary advanced RCA — fails |
| 2 | Failure Detector | NON_LLM | Evaluator | Classifies outage type |
| 3 | Fallback Decision | NON_LLM | Router | Choose SLM fallback |
| 4 | SLM Fallback | SLM | Fallback | Continues with degraded quality (~0.72 confidence in demo) |

**What to say**

> This pattern is not about saving tokens. It is about continuity. When the architect is unavailable, the service desk still answers — with an honest quality downgrade.

**Evidence**

- Failure mode selector in UI  
- Frontier attempt error + detector + SLM fallback  
- Resiliency callout (availability over optimization)

---

### 10.3 Model Comparison (dropdown)

**Purpose:** Segment-level decision audit.

| Element | Technical meaning |
|---|---|
| Per-pattern tables | Rows from `PatternResult.segments` |
| Selected columns | Actual chosen model path (tokens, latency, confidence, provenance) |
| Alternative columns | ESTIMATED counterfactual (`SegmentResult.alternative`) |
| Decision / why | Human-readable rationale from the pattern engine |
| Avoidance callout | From `ArchitectDecision` |

Router child rows `REQ-*` are hidden in the table so the view stays readable; aggregates remain in Router pattern detail and MLOps.

**Demo talking point**

> Operations shows the portfolio. Comparison shows the verdict on each segment — why SLM won, or why Frontier was justified.

## 14. Suggested live demo sequence (technical)

1. Start UI with saved results already present (`DEMO_MODE=true` for reliability).  
2. **Overview** — status strip, KPIs, name the five tiles.  
3. Open **Planner-Worker** — architecture diagram, Load result, walk Why / Tokens / Architect Decision.  
4. Optionally open **Cascade** or **Fallback** for quality/resilience contrast (2–3 minutes).  
5. **AI Model Operations** — charts 2, 9, 11 + efficiency table.  
6. **Model Comparison** — one pattern table, read one “why” aloud.  
7. Close on the principle and the primary metric: Frontier tokens avoided with quality preserved where it matters.
